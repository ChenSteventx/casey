## 这轮学到什么

1. **新观察源要过「与既有账本消费方合流」检验**。读回门契约给 open 加观察时只验了
   自身链路（金牌 S1e 归档全档），没沙盘「同 flow 已有 create 观察时下游怎么读」——
   C3 守卫与 H1i 早已钉死多观察形态，十二跑才撞上。给共享账本（identityObservations）
   添加新写入方时，要遍历既有读取方（守卫/issuer/基数门）做形态推演。
2. **让位判据选 platformId 不选 name/role**：同名可撞（正是 C3 拦的），role/atom 过滤
   反而窄——同 platformId 是「同一平台实体」的最强判据，且列表扫描的 nonEmpty 字符串
   约束保证了 `===` 可信。评审双方都独立认可这点。
3. **评审环境故障要如实分轨**：pi 首轮死于 drvfs 挂载故障，其 CHANGES_REQUIRED 是
   执行态不是代码结论——存证 HARNESS_ERROR、对同一快照重跑，绝不把环境红当发现、
   也绝不静默丢弃重来。快照不可变性（4d05447 两轮同字节）让重跑有意义。
4. **drvfs 故障两次实证同会话**：开场一次（用户重挂复原）、双审中一次（WSL 重启复原）。
   长会话跨小时的 /mnt/d 依赖操作（评审、扫描）要有「环境死了就存证重跑」的预案，
   产物尽量落 ~（本会话扫描/收据/红证都在 ~/casey-tools，事故零损失）。
