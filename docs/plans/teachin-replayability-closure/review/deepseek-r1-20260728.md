## Finding 1 — HIGH — `lib/teachin/entity-lock-verifier.mjs:199-203`

**问题**：fail-open 缝。`verify()` 函数在 `admission` 返回 `ok:false` 时，仅当 `reason` 属于 `MALFORMED_ADMISSION_REASONS`（7 个枚举）才立即拒绝。不在白名单内的 admission 失败原因（当前至少缺 `REPLAY_EVENT_POLICY_INVALID`）会**穿透**到后续的 entity verification 分支，而非首错停止。

**证据**：
- `checkReplayEntityAdmission`（`lib/entity-semantic-lock-preflight.mjs:846`）对未知 atom 返回 `REPLAY_EVENT_POLICY_INVALID`，属于事件结构本身非法（atom 不在已知 recipe 注册表中）
- `MALFORMED_ADMISSION_REASONS`（entity-lock-verifier.mjs:24-31）共 7 个条目，不含 `REPLAY_EVENT_POLICY_INVALID`
- 亲跑验证：
```
$ node -e "... admissionReasons.filter(r => !malformed.has(r)) ..."
REPLAY_EVENT_POLICY_INVALID        ← 不在白名单
REPLAY_READ_EVENT_TARGET_INVALID   ← 不在白名单
```
- 逻辑路径：L199 `if (admission?.ok !== true)` → L200 取 reason → L201 `MALFORMED_ADMISSION_REASONS.has(reason)` 不命中 → **不下 denied，继续执行** → L203 `noEntityRequired`（false，因为 admission 不 ok）→ L217 `hasAuthority` 分支

**建议修法**：将 `REPLAY_EVENT_POLICY_INVALID` 和 `REPLAY_READ_EVENT_TARGET_INVALID` 加入 `MALFORMED_ADMISSION_REASONS`，确保所有"事件文档本身不合法"的 admission 拒绝原因在 L201 统一被挡住。注意 `FROZEN_ENTITY_*` 系列是 entity authorization 失败，**不应**加入此集合（当前设计正确地将它们留给 entity verification 处理）。

## Finding 2 — MEDIUM — `lib/teachin/raw-axes-adapter.mjs:217-242`

**问题**：消费次序导致不可逆资源损耗。`projectAndVerify` 先消费 `rawObservationAuthority`（L217）和 `resolvedProjectionAuthority`（L229），**然后**才做 `bindingsAgree(raw, resolved)`（L242）。绑定不符时两枚一次性 authority 已经烧掉，调用方无法恢复。

**证据**：
- L217: `dependencies.consumeRawObservationAuthority(...)` 消费第一枚
- L229: `dependencies.consumeResolvedProjectionAuthority(...)` 消费第二枚
- L242: `bindingsAgree(raw, resolved)` 校验绑定 ── 此时两枚均已 consumed
- 对照 `resolved-projection.mjs:72` 注释："capture capability 先验真，否则伪造 capture 会白白吃掉 genuine clean proof" ── 同模块内对类似问题有明确意识，但此处的门是倒置的

**建议修法**：将 `bindingsAgree` 提升到两个 consume 之前；仅在绑定吻合后才消费 authority。这不需要触及 authority 模块的 WeakMap 协议，只需调整调用次序。

## Finding 3 — MEDIUM — `lib/teachin/verdict-cli-adapter.mjs:95 + 105-111`

**问题**：TOCTOU 竞态窗口。L95 对 `dependencies.readJudgeBytes()` 返回的 `judgeBytes` 做 sha256 校验，L105-111 通过 `dependencies.executeJudge()` 调用 `execFile(process.execPath, [JUDGE_PATH, ...])`——node 重新从磁盘读取 `JUDGE_PATH`。两步之间文件可被替换。

**证据**：
- L95: `judgeBytes = dependencies.readJudgeBytes()` → sha256 校验通过
- L105-111: `execFile` 以 `JUDGE_PATH`（磁盘路径，L18 解析自 `import.meta.url`）为参数，node 重新 `readFile` 该路径
- 两读之间无原子性保证；同一进程内替换 `bin/verdict.mjs` 即可绕过完整性校验
- FROZEN_JUDGE_SHA256 当前值正确（亲跑 sha256 吻合），但校验对象与实际执行对象不同步

**建议修法**：将 `judgeBytes`（已校验的 Buffer）写入临时文件，以临时文件路径执行而非原始 `JUDGE_PATH`；或在 `execFile` 后对进程输出做签名验证。利用 `require('node:fs').mkdtempSync` + `writeFileSync` 可零依赖解决。

## Finding 4 — MEDIUM — `lib/dual-replay/replay-completion.mjs:309-329`

**问题**：`openRunExecution` 无 consumed 标志，同一 `runExecutionAuthority` 可被反复开箱，获取 runtime capability（`freshRuntimeAuthority` / `topologyAuthority` / 全部 artifacts 字节）。`EXECUTION_STATE`（L17）只有 set/get，没有 consumed 置位。

**证据**：
- L309-329：`openRunExecution` 只读 `EXECUTION_STATE.get(runExecutionAuthority)`，不置任何 consumed / executed / sealed 标志
- `runExecutionAuthority` 引用从 `raw-event-observation.mjs:402` 和 `runtime-cycle-adapter.mjs:263` 进入返回对象，超出 `replay-completion` 模块闭包
- 目前 canonical 路径在 L111/L139 做 identity check（`result.runExecutionAuthority !== runExecutionAuthority`），但这是**同源性核**而非一次性消费

**建议修法**：为 `EXECUTION_STATE` 的 entry 增加 `opened` 字段，`openRunExecution` 首次返回后设 `opened = true`，二次调用返回 `null`（非消费性 inspect 不受影响，因为目前没有 inspect 通道）。注意 `completeResolvedSourceReplay` 内部对 execution 的读取也要适配——如果它依赖 `openRunExecution` 的副作用，需要调整为调用一次后缓存。

## Finding 5 — MEDIUM — `lib/teachin/replayability-cycle-entry.mjs:92`

**问题**：死事件监听器。`recordingBrowser.on('disconnected', () => { contextClosed = contextClosed || false; })` 是恒等操作——无论 `contextClosed` 是 `true` 还是 `false`，`OR false` 都不改变其值。browser 断连事件无法更新闭合状态。

**证据**：
- `contextClosed` 初始化为 `false`（L88）
- context close 事件处理器：`recordingContext.on('close', () => { contextClosed = true; })` ── 正确
- browser disconnect 事件处理器：`() => { contextClosed = contextClosed || false; }` ── 恒等，永远不改值
- 亲跑确认唯一命中点在 L92：
```
$ grep -rn "contextClosed = contextClosed || false" lib/
lib/teachin/replayability-cycle-entry.mjs:92: ...
```
- 极边情形：browser 先于 context 断开且 context close 事件未触发 → `contextClosed` 保持 false → finally 块（L130-139）走关闭 context/browser 清理路径（会抛异常但被吞掉）。功能影响低但明确是代码缺陷。

**建议修法**：改为 `() => { contextClosed = true; }`，与 context close 处理器一致。

## Finding 6 — MEDIUM — `lib/teachin/fresh-runtime.mjs:59-61 + 110-113`

**问题**：witness 无 consumed 标志。同一枚录制闭包 witness 可通过 `authorizeFreshReplayRuntime` 重复铸出多枚 fresh runtime authority（只要每次换新 replay 三件套对象）。`WITNESS_STATE`（L6）只有 set/read，无 consumed 账本；`USED_REPLAY_OBJECTS`（L7 WeakSet）只锁 replay 对象不锁 witness。

**证据**：
- L59-61: `WITNESS_STATE.set(witness, record)` ── 没有 `consumed` 字段
- L110-113: `readWitness(witness)` ── 只有内部 `readWitness`，无 consume 路径
- L126-130: `USED_REPLAY_OBJECTS` 阻止同一 replay 对象重复铸权，但不阻止同一 witness + 新 replay 对象
- 这意味着「一次录制关闭 = N 个 fresh runtime」——若设计意图是 1:1（一次录制产生一次 replay），这里语义上过宽

**建议修法**：如果设计意图为 1:1，在 `authorizeFreshReplayRuntime` 成功路径上对 witness record 增设 `authorized = true` 并在 L110 的 `readWitness` 之后检查该标志。如果 N:1 是预期语义（同一个录制可以被多次 replay），建议在 `WITNESS_STATE` 旁边加注释说明不回放独占语义。

## 终判

**CHANGES_REQUIRED**

原因：Finding 1（`entity-lock-verifier.mjs:199-203`）是确定性的 **fail-open 缝**——`REPLAY_EVENT_POLICY_INVALID`（未知 atom 的事件）可绕过 malformed admission 首错停止，落入 entity verification 分支。这是安全属性级别的缺陷，需要修单合入后才能 APPROVE。

其余 5 个 MEDIUM 发现均为边界/健壮性问题，不单独构成拦停，但建议在下一轮修单中逐项处理（TOCTOU、消费次序、witness 复用语义、dead listener、openRunExecution 复用）。
