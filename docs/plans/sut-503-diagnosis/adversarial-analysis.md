> 证据截止：2026-07-27；已纳入①真机差分定位
> `docs/plans/sut-503-diagnosis/evidence/live-differential.md`。
> 本文只读源码、`real-uat-attestation` 见证账和本地既有 run 产物；未连接、启动或访问任何

## 0. 反证对象与当前结论

待检强假设：

> 经标准新增表单创建的骨架智能体，打开详情页会稳定触发
> `agentPlus/queryPlus` 与 `agent/setup/getAgentDetail` 两条 `503`。

现有证据支持的更窄事实是：

1. 2026-07-23 的两个不同 19 位平台 ID 实例，在同一测试账户、同一测试名称、相近的“创建后即打开”
   流程下，均出现同一对 `503`。run-1 的两条请求归因到打开步，run-2 的两条请求归因为空。
2. 两次失败都发生在唯一卡片、身份读回成功且已进入正确详情路由之后；“工装误点了另一张卡”与
   “详情路由完全没带参数”不符合现有证据。
3. 2026-07-24 的第三个不同平台 ID 编译观察件已构成一条高价值候选反证：
   使用与 run-2 相同的测试名称和编码，记录两个端点均为 `200`。该件只有编译观察、没有同次正式回放
   与创建日志，本身不能宣告缺陷已消失。
4. ①于 2026-07-27 新建了预检为零、列表唯一的全新 `atl_` 骨架实例；创建后首次打开即得到双
   `200`，页面失败提示计数为 0，截图与录屏未见失败提示。这是有效 HTTP/视觉诊断样本，直接反证
   “任何标准表单新建骨架实例首次打开都稳定双 `503`”。
5. 本地四次成熟智能体历史 axes 中，这两个端点也都为 `200`。因此，现有证据更像“某一创建配置、
   初始化状态、创建到首次打开的时序或当时后端状态”触发，而不是两个端点永久不可用。
6. run-2 的 `PASS` 只反映 Casey 的请求归因作用域：请求发起时没有活动步，故
   `attributedStepId=null`，零 `LLM` 裁判不会用它背书本步 `SUT_DEFECT`。它不否定两条 HTTP `503`
   实际发生。

总状态：**证伪（强假设）**。“标准表单新建骨架智能体首次打开稳定双 `503`”已被 2026-07-27
全新唯一实例首次打开双 `200` 反证；“2026-07-23 两个不同实例在当时精确流程下真实复现双 `503`”
仍受正式回放证据支持，历史 `SUT_DEFECT` 不被改写。服务端根因保持未决。

## 2. 替代解释逐项评估

### A1. 单一坏实例或单一平台 ID

- **假设**：只有 run-1 那一条业务记录损坏，双 `503` 与“骨架智能体”无一般关系。
- **可观察预测**：换一个新平台 ID 后两个端点应恢复 `200`，或至少不再以同一对端点同时失败。
- **现有证据**：run-2 使用新的 19 位平台 ID，仍出现同一对 `503`；run-1 与 run-2 编码也不同。
  这否定“只有 run-1 这一行坏数据”。E5 的第三个不同平台 ID 为双 `200`；① r3 又用预检为零的新
  唯一实例在首次打开时得到双 `200`。实例批次、配置或创建时点仍可能决定结果。
- **状态**：**证伪（窄版）**。单一坏实例解释不了 7 月 23 日两次失败；所有新实例同病也已被 r3
  反证。
- **下一条最小安全试验**：不再为“是否任一新实例必现”继续造件。若研发日志指向初始化延迟，再在
  修复验证时对一个实例补立即/短等/重开三点即可。

### A2. 账户或权限不足

- **假设**：测试账户无权访问两个详情端点，后端错误地把权限问题包装成 `503`。
- **可观察预测**：同账户打开任意智能体时，这两个端点都失败；或脱敏响应体/响应头呈权限、租户、
  身份域错误，而不是资源初始化错误。
- **现有证据**：两次失败页的其他详情端点大多 `200`；本地成熟智能体历史、E5 第三实例及① r3
  新实例上，这两个端点均有 `200`。①沿用 HANDOFF 中 Steven 已带外确认测试账户的历史前提，r3
  两响应又是正常 JSON 成功形态。
- **状态**：**证伪（账户全局无权）**。资源级权限包装异常理论上仍可能，但已不是优先分叉。
- **下一条最小安全试验**：不再做额外账户探针；研发只需从 7 月 23 日服务端日志核当时请求是否经过
  权限/租户分支。

### A3. 精确同名敌意预置导致误选或后端冲突

- **假设**：第二张同名卡已经在场，工装选错卡或后端按名称取到了另一条记录。
- **可观察预测**：首次失败时应有多候选、身份读回不等，或在敌意预置出现前不能复现。
- **现有证据**：run-1/run-2 的失败回放①均为 `candidateCount:1`、`resolution:unique`、
  `identityReadback.ok:true`；敌意同名第二件是在失败回放①之后才创建。随后回放②正确落
  `AMBIGUOUS_ACTION` 且不点击。
- **状态**：**证伪**。敌意预置不是两次回放①双 `503` 的前因。
- **下一条最小安全试验**：无需为“同名卡误点”再建复杂场景；①只需在新实例首次打开前保留
  `candidateCount=1` 与身份读回证据。名称复用造成的后端软删冲突另见 A8。

### A4. 缓存、最终一致性或“创建后即打开”时序

- **假设**：创建主记录先成功，详情子表、扩展配置或缓存稍后才初始化；首次立即打开会双 `503`，
  等待或重载后恢复。
- **可观察预测**：同一实例的状态应随创建后经过时间变化：立即 `503`，稍后或刷新后 `200`；无需改
  名称、编码或账户。若是一次后端事故，则不同日期也可能从双 `503` 变双 `200`。
- **现有证据**：run-1/run-2 都是新建后进入详情，未留同实例重复打开矩阵；E5 在次日出现同名称、
  同编码的新平台 ID 双 `200`；① r3 的全新唯一实例在创建后首次打开也双 `200`。这证伪“任何首次
  立即打开都失败”，但仍无法区分 7 月 23 日当时的最终一致性窗口、浏览器缓存、后端发布修复或短时
  服务事故。
- **状态**：**支持（作为高价值替代解释）**。
- **下一条最小安全试验**：先查 7 月 23 日两个失败时点前后的服务日志、部署记录与创建事务；只有
  日志指向延迟初始化时，才补同一实例“立即 / 短等 / 重开”三点，不做长期压测。

### A5. 请求归因作用域造成 run-2 假干净

- **假设**：run-2 的 `PASS` 不是页面无错，而是请求在 Casey 清空活动步之后才发起，因而不能背书
  本步 `SUT_DEFECT`。
- **可观察预测**：axes 中仍能看到两个 `503`，但 `attributedStepId=null`；视觉终帧仍可能显示失败；
  `verdict.mjs` 应保持 `PASS`，因为它只消费归因到本步的错误。
- **现有证据**：E3、E4 与 E7 完整符合。源码在动作后把 `currentStepId` 清空，再做代表步静默采集；
  无活动步请求归因为空，随后作为孤儿记录并入首 intent，裁判明确拒绝用空归因 5xx 背书本步。
- **状态**：**支持**。
- **下一条最小安全试验**：无需修改生产或裁判。①只需在差分账同时列“请求实际状态”和
  “`attributedStepId`”，禁止用 `PASS` 代替前者。若要改变归因语义，应另立 Casey 工装契约，不能在
  本缺陷诊断里顺手改。

### A6. 详情路由参数完全缺失

- **假设**：工装打开了详情 URL，但没有提供详情 API 所需标识，故 `getAgentDetail` 返回 `503`。
- **可观察预测**：失败请求应没有 `promptTemplateId`，为空，或形状明显不合法。
- **现有证据**：run-1/run-2 的 `getAgentDetail` 都带 19 位 `promptTemplateId`；相邻
  `getRequestApi` 使用同一参数并返回 `200`。① r3 的成功 `getAgentDetail` 同样带 19 位纯数字形态。
  因此“参数完全没带”与证据冲突。
- **状态**：**证伪（仅完全缺失）**。参数指向错误业务类型、详情子表未初始化或 ID 映射错误仍未决。
- **下一条最小安全试验**：客户端参数形状证据已够；研发在服务端对比 7 月 23 日失败请求与
  7 月 27 日成功请求的 ID 解析、详情子表查询结果即可。

### A7. 表单字段、下拉首项或自动编码造成无效组合

- **假设**：创建页接受了一组表面合法、详情层却不支持的字段组合；或名称触发自动编码覆盖，导致
  主记录与详情子记录不一致。
- **可观察预测**：改变一个表单维度后，双端点状态会变化；创建接口响应可能成功但缺少详情初始化
  所需字段。若自动编码是唯一原因，显式回读并固定编码后应恢复。
- **现有证据**：run-1 使用平台自动生成编码，run-2 最后显式写入并回读不同编码，两者都双 `503`，
  所以“某一个编码值”或“自动编码覆盖本身”不足以解释。创建脚本还选择输出类型、类型、记忆体类型、
  回答收集器类型，其中三个采用首项；这些值、角色编码是否实际在场及服务端初始化效果没有差分。
  E5 同名称、同显式编码却双 `200`，进一步说明编码不是充分条件。① r1/r2 因输出类型定位门在确认
  创建前中止，0 目标响应、0 打开尝试，不能当差分样本；r3 创建成功，但没有 B 件，输出类型差分仍
  未隔离。
- **状态**：**未决**；自动编码单因已弱化，字段组合或初始化链仍值得优先查。
- **下一条最小安全试验**：先由研发比较 7 月 23 日失败实例与 7 月 27 日成功实例的服务端创建字段和
  初始化结果。只有发现明确字段差异时，再做一组单变量 UI 复验；不要重跑 r1/r2 或把它们记成红样本。

### A8. 删除后悬挂、软删残留或名称复用

- **假设**：UI 删除只隐藏主记录，详情子表或缓存仍以旧名称/编码占位；重建同名实例命中悬挂关系。
- **可观察预测**：使用从未出现过的名称和编码应恢复；复用旧名称/编码更容易失败。UI 查询归零并不
  足以反证后端软删。
- **现有证据**：run-2 后的名称与两个编码查询均归零，但这只是 UI 可见面。run-2 确实复用了 run-1
  名称，可能受 run-1 删除残留影响；然而 run-1 的 `503` 发生在本轮最终清理之前，所以“run-1 的删除
  导致两次失败”不成立。更早是否存在同名软删记录未知。E5 后来又复用同名称、同编码并双 `200`，
  使“只要复用就必失败”不成立；① r3 又用预检为零的新唯一名称首次打开双 `200`。
- **状态**：**证伪（普遍软删/名称复用解释）**。它不能同时解释 run-1 与后续成功样本，不再列研发
  首查方向。
- **下一条最小安全试验**：无需再建删除矩阵。① r3 的清理只背书精确名称 1→0；编码面未独立证明，
  如需运维清理由人单独核，不影响本次 HTTP 反证。

### A9. 工装误点、身份读回错误或详情页并非目标实例

- **假设**：Casey 点中了同名错误卡、列表外同名控件，或点击后没有确认业务身份；`503` 属另一实例。
- **可观察预测**：动作轴应为多候选、回读失败，或 URL 不进入详情路由；已签平台 ID 与网络信封/DOM
  证据不能同时一致。
- **现有证据**：两次失败回放①均为唯一候选、身份读回成功；见证账记录网络信封 + DOM 物理卡片双证
  与已签平台 ID 全等，且 `urlPathname` 已进入详情路由。回放②在真正多候选时又能证明工装拒绝点击。
- **状态**：**证伪**。
- **下一条最小安全试验**：①继续复用现有身份门，不需新增更重安全工程；把“候选数、读回是否相等、
  详情路由是否到达”三项随每次探针列入账即可。

### A10. 一个端点失败连带造成另一个端点失败

- **假设**：`agentPlus/queryPlus` 先失败，前端或后端再连带触发 `getAgentDetail` 失败；实际只有一个
  根故障。
- **可观察预测**：第二请求应在第一请求完成后才发起，或禁用/恢复第一端点后第二端点随之变化。
- **现有证据**：run-1/run-2 的请求发起时间只差约数毫秒，中间还并发发起多个 `200` 端点；
  `getRequestApi` 用同一详情参数为 `200`。这不支持“浏览器收到第一个失败后才发第二个”的串行级联。
  ① r3 中两个端点又同时恢复 `200`。两个服务共用同一未初始化子表、网关或下游依赖，仍可解释
  7 月 23 日同涨同落。
- **状态**：**未决**。前端串行连带已弱化，共享后端依赖仍可能是单根因。
- **下一条最小安全试验**：研发优先按一个共同故障簇查 7 月 23 日服务日志；有证据证明根因独立后
  再拆两张缺陷单，不要求测试侧继续隔离服务。

### A11. 整页、隧道、代理或当时全局服务故障

- **假设**：不是实体数据问题，而是整页网络、回环隧道、网关或后端在当时普遍异常。
- **可观察预测**：同页多端点应共同 5xx，成熟对照实体也应失败；不应只稳定命中两个详情端点。
- **现有证据**：两个失败样本中，列表、知识、工具、参数、请求配置等相邻端点均 `200`，仅目标两个
  端点 `503`；成熟实例历史与 E5 的目标两个端点又能 `200`。这强烈弱化整页/隧道故障，但不能排除
  当时两个后端服务共同短时异常或随后已发布修复。① r3 在恢复后的单实例隧道上首次打开新实例，
  两目标端点双 `200`、页面无失败提示，进一步证明当前环境不可复现。
- **状态**：**证伪（整页/隧道故障）**；**未决（两服务短时事故或发布变更）**。
- **下一条最小安全试验**：停止全站探针；研发对照 7 月 23、24、27 的服务发布与错误日志即可。

### A12. 真缺陷与用例/工装错误混淆

- **假设**：身份用例本来只要求“点对并进入详情”，两个辅助端点失败不该算 `SUT_DEFECT`；或者
  `verdict` 被模型印象翻成缺陷。
- **可观察预测**：若无已签硬断言或动作身份存疑，确定性裁判应落 `NEEDS_HUMAN`，而不是
  `SUT_DEFECT`；若只是模型意见，`verdict.json` 不应有确定性证据链。
- **现有证据**：run-1 动作唯一、身份读回成功、详情路由断言通过，但已签
  `noErrorEnvelope` 硬断言实际为 2，且本步有两条归因 503/失败信封背书；零 `LLM` 的
  `verdict.mjs` 因此机械落 `SUT_DEFECT`。终帧“操作失败”又独立支持页面确有用户可见异常。
  run-2 则因归因为空机械 `PASS`，证明裁判没有凭模型印象追着画面改四态。① r3 是浏览器诊断探针，
  不是 Casey 裁判：其 exit 2 发生在两条 HTTP `200` 已收到之后的后置证据门，既不生成新四态，也不
  改写历史四态。
- **状态**：**支持（窄结论）**。在 run-1 的已签契约内，这是有背书的 `SUT_DEFECT`，不是
  `HARNESS_ERROR` 或 `CASE_DEFECT`；强缺陷标题已被 r3 反证。
- **下一条最小安全试验**：保持 verdict 原样。缺陷报告分开写：“run-1 已裁 `SUT_DEFECT`”
  “run-2 实际双 `503` 但裁定作用域外”“7 月 24/27 双 `200`，当前不可复现”。

## 3. ①退出码与样本资格复核

1. r1、r2 都在确认创建前因输出类型定位门 fail-closed 中止，0 目标响应、0 打开尝试；exit 1 是
   工具探针失败，不是 `SUT` 红样本。
2. r3 已创建 A 件并首次进入详情，两目标端点双 `200`、失败提示 0；随后“卡副标题等于编码”的
   后置证据假设不成立，故脚本 exit 2。后置门不能倒写此前已收到的 HTTP 事实，所以 r3 是有效
   HTTP/视觉诊断样本，但不是正式 verdict。
3. 专用清理证明 A 精确名称从 1→0，B 从未创建且保持 0；编码面因 DOM 假设错误未独立证明。
   本文只采名称清理事实，不把编码 0 冒充归零证据。
