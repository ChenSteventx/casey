## 一、要解决的事实（已实证，非推断）

2026-08-10 三例回放批次里 `tc_wf_publish_states` 的清理链失败、真机残留一条。根因用录像
抽帧看死（证据全文见 `docs/plans/p9-created-workflow-cleanup-continuity-v3/evidence/
replay-cleanup-failure-20260810.md`）：

- 卡片布局下删除入口藏在悬停浮现的「更多操作」菜单里，`performCardMenuDeleteTrigger`
  点完菜单中的「删除」项后**直接返回**，`finally` 里的 `dispose(menu)` 只释放句柄引用、
  **不关闭菜单**；
- 随后确认步 `performWorkflowDeleteConfirm` 去点「确认」，此刻菜单仍开着，点击被拦，
  Playwright 立即判元素不可交互，**1ms 返回 `actionError`**；
- 对照组 catalog 同一步耗时 758ms 成功——抽帧显示它执行时菜单已基本关闭。

**为什么两例有差**：publish 建的工作流是**已发布**态，操作菜单比未发布态多一个「停用」项，
菜单更高、关闭动画更长；回放推进到确认步比菜单关完更快。publish 的后一帧（+0.5s）显示
菜单关闭后确认按钮清晰可点——**只差不到 0.6 秒**。

**为什么编译期没踩到**：编译期每步之间有观察停顿，天然慢一拍。这是一条**只在回放期显形的
时序竞态**，与 08-08 编译期 20 步全绿并不矛盾。

## 二、决策树

### D1　离场判据用什么？——**取可见性，不取 DOM 移除**

`assert-visibility-semantics` 契约的真机探针已实测过同类浮层：关闭后 **DOM 命中仍 1、
可见命中 0**——浮层视觉关闭但节点不卸载。若判据取 detached，等到超时也等不到。

本文件第 385-388 行已有成熟判据（`display !== 'none' && visibility !== 'hidden' &&
visibility !== 'collapse' && rect.width > 0 && rect.height > 0`），复用其反面即可，
口径与既有代码一字不差。**detached 也算离场**（节点真卸载时同样满足「不可交互」）。

**定案：离场 = 节点已卸载 或 按既有三合一判据不可见。**

### D2　等待预算多少？——**3000ms 轮询 50ms**

同文件既有三个等待常量全是这个模式（`CAUSAL_DIALOG_TIMEOUT_MS` /
`CAUSAL_MENU_TIMEOUT_MS` / `TARGET_RECORD_TIMEOUT_MS` 均 3000 + 50）。对照组实测菜单关闭
约在确认步前完成、publish 差的不到 0.6 秒，3 秒余量充足；且远小于回放看门狗 120 秒。

**定案：`MENU_DISMISS_TIMEOUT_MS = 3000`、`MENU_DISMISS_POLL_MS = 50`，与既有常量并列。**

### D3　等待超时后怎么办？——**取丙：继续点 + 动作轴留痕**（Steven 2026-08-10 裁）

原提三案见第三节。**Steven 裁定取丙，未取我推荐的甲。** 理由归位：留痕的可观测性价值压过
回归成本——超时若不留痕，事后只能从耗时反推，而「菜单未在预算内离场」正是本次事故里最该
被看见、却恰恰看不见的那条事实。这与护栏 #14「证不出的要能被看见」同向。

据此本契约的实现面比取甲时大：动作轴要加字段，牵动三轴投影与既有金牌，须按护栏 #19 复跑
全部受影响的 browser-replay 金牌。加的是**加法字段**（不改任何现有字段语义），下游不读它
即不受影响；真正会红的是逐字钉轴形状的金牌，那些红是预期的、须逐个核过再改。

### D4　落点在哪？——**`performCardMenuDeleteTrigger` 返回成功前**

它是唯一持有菜单句柄 `menu` 的地方（第 616 行 `menu = causal.dialog`）。确认步那侧
（`performWorkflowDeleteConfirm`）拿不到菜单句柄，若在那里等就得重新扫描浮层、既慢又可能
抓错浮层（`MENU_SELECTOR` 与 `DIALOG_SELECTOR` 虽逐 token 互不相交，但重扫是新的不确定性）。

**定案：落在 `performCardMenuDeleteTrigger` 里、菜单删除项点击成功之后、`return picked` 之前。**

### D5　影响面多大？——**只卡片布局，表格布局零触碰**

`performCardMenuDeleteTrigger` 只在 `performWorkflowDeleteTrigger` 判 `result.resolution
=== 'none'`（记录容器内无直见删除钮）那一支被调用。表格布局直接点行内删除按钮、根本不开菜单，
这条路径不经过。

**定案：改动只加在卡片布局分支内，表格布局与多命中具名拒的行为一寸不动。**

### D6　金牌怎么钉？——**必须复现「菜单不关」，不许纯函数交差**

照 `assert-visibility-semantics` 契约 D5 的先例：假环境夹具若「关闭即清空内容」就复现不了
真机接缝。本轮须有一个**「点完菜单项后菜单仍可见一段时间」**的夹具情景，让红先行基线走完整
回放路径（事件运行器 → 三轴），不许直接调等待函数交差。

矩阵：菜单立即关闭 → 不额外等、行为与改前逐字同；菜单延迟关闭（小于预算）→ 修前确认失败、
修后确认成功（锁真实红签名）；菜单始终不关（超过预算）→ 行为由 D3 定案决定；
等待期间菜单被卸载 → 视为离场、立即继续。

## 三、须人裁：D3 超时处置

菜单在 3 秒预算内没离场时，三条路：

**甲、继续点（最小侵入，我的推荐）**
超时就照原样往下走，让确认步自己去点、自己失败。理由：fail-safe 已由下游保证——点击失败
落 `action_failed`，裁定判 `NEEDS_HUMAN(INDETERMINATE)`，绝不会假绿（本次事故里裁判正是
这么工作的）。代价：超时这件事本身**不留痕**，事后只能从耗时反推。

**乙、超时即具名拒（fail-closed）**
超时直接返回 `action_failed` 并具名拒因，不再尝试点击。好处是拒因精确、一眼看出是菜单没关；
代价是把「菜单没关但确认其实点得动」的情形也判死——而这种情形真机上可能存在（菜单与对话框
不重叠时点击未必被拦）。

**丙、继续点 + 动作轴留痕**
超时仍继续点，但在动作轴上加一个字段记录「菜单未在预算内离场」。信息最全，但改轴形状会牵动
三轴投影、裁定消费面与既有金牌，属加法但影响面最大。

我的推荐是甲，理由是本次事故已证明下游 fail-safe 有效、没有假绿风险，而甲对现有轴形状与
消费者零改动、回归面最小。乙的「误杀可点情形」风险在真机上不可忽略；丙的信息价值当前不足以
抵消动轴形状的回归成本，可作为后续欠账。
