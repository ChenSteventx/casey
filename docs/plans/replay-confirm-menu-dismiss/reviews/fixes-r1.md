# 按 R1 评审改了什么（pi APPROVE + grok APPROVE，均 0 Critical / 0 High）

两路都判 `APPROVE` 不阻断，但共提出 5 条 Medium。逐条处置如下——**不是「已知悉」了事，
凡能改的都改了，改不动的写清为什么不改**。

## 1. R12 仍在假前提上做断言（grok Medium）→ 已改

原 R12 名为「菜单点后不关闭时确认弹层因果授权仍唯一」，却在**不建模遮挡**的夹具上断言
`confirmed.resolution === 'unique'` 与出站请求 1 条。真机上菜单开着时确认点击被 hit-target
拦下，所以这两条断言建在一个真机不成立的前提上。前一轮我只在注释里写了「R12 因此是假绿」，
没动 R12 本身——评审逮的正是这个。

处置：把 R12 收窄到它真正证得住的命题——菜单还开着时，弹层选择器不得把菜单当成确认弹层
（保留 `trigger.resolution` 与 `found.resolution` 两条断言），删去 `confirmed` 与请求条数两条；
确认落笔的成败归 R27。并在检查体上方写明它**故意不建模遮挡**。

**收窄后验它不是空检查**（否则等于用一个无害的空壳换掉一个假绿）：突变 `DIALOG_SELECTOR`
加入 `.hr-dropdown`（让菜单被当成弹层），R12 实红——
`触发解析态：期望 "unique"，实得 "action_failed"`，26/28；还原后 sha256 逐字节一致。

## 2. 夹具遮挡模型粗于真机（pi Medium M2 + grok Medium，两路共指）→ 已改注释

夹具是 all-or-nothing：浮层在场就拦一切浮层外点击；真机 Playwright 的 hit-target 在元素中心
采样 `elementFromPoint`，只拦视觉上真被盖住的目标。故夹具**严于**真机。本契约复现的场景里
菜单确实盖住确认钮（录像抽帧实证），命题内忠实；但推广到不重叠场景会把真机本该绿的钉红。

处置：按两路共同建议，在夹具 `click()` 的遮挡判定处写明模型边界与「不要推广到不重叠场景、
要那种情景须先引入点位几何」。不改行为——引入几何采样是另一个契约的事，本刀不夹带。

## 3. 红基线偏字段、不是「确认真被拦」（grok Medium）→ 已补功能红签名

原 `accept/red-baseline.txt` 三条红先行签名全是「字段 `undefined`」，钉的是加法字段在场，
不是功能事实。评审这条判得准。

处置：补突变三「不真等、只伪造证据 `menuDismiss: { dismissed: true, waitedMs: 0 }`」的实测红——
证据字段齐全且自称已离场，但因为没真等，R26 的确认落笔实测 `action_failed`（26/28）。
红基线现载明：功能红签名取突变三的 R26，字段红签名取修前基线，**两者并存、不可互相替代**。

## 4. 我 accept 里的数字不实（grok 实测逮出）→ 已改正

原 `red-baseline.txt` 写「突变二（可见性判据反转）→ 2 条红」。本方复跑实测 **3 条红**（25/28），
grok 对、我错。已改正并把实录三行贴进文件，同时注明是笔误、由评审实测坐实后改。

## 5. 32 金牌 / 7 陈旧红：未复跑、无清单（grok Medium + NEEDS_HUMAN）→ 已补跑，且数字本身是错的

评审判 `NEEDS_HUMAN` 判得对：提交信息声称「串行复跑 32 份，7 份红经主树干净基线对照证实为
陈旧红」，而 plan / accept / commit 之外都没有那 7 份的路径清单，异构评审无从独立核对。

处置：定死一条**可重跑的选集规则**（文件名含 `replay` 或 `delete`，并上引用删除域的，再筛
零 SUT 与静态两类）后复跑，逐份退出码落 `accept/affected-goldens.txt`。真实结果 **50 份、
49 绿、1 红**。那两个数（32 / 7）都是错的。

唯一真红 `real-run-trust` 属既有陈旧红，证据是本刀 `git show --stat HEAD` 不含
`bin/replay.mjs` 与该金牌任一文件，不可能由本刀引入（该金牌要求生产件含旧式逐参解析
`o.uniqueName = argv[++i]`，而生产件早已改为对象解析）。

先前那 7 份「红」不可复现。最可能的成因在本轮当场再现了一次：`/mnt/d` 9p 静默断连期间，
第一次跑批从第 21 份起连续 30 份全 exit 1，其中包括已被两路评审各自独立跑到 28/28 的
`wf-delete-card-layout`——磁盘故障伪装成断言失败。跑批脚本随后改成同抓 stderr，非零退出里
含 `EIO`/`ENOENT` 的记 `INVALID_IO` 而非 `RED`；重跑得到上述 50/49/1，`INVALID_IO` 计数 0。

## 未改的一条，及为什么

pi Medium M1：`menuStillShown` 的 `evaluate` 抛错按「已离场」处理，页面崩溃时会少等该等的
时间。**pi 自己明确建议不改**——区分需要额外的健康探针、引入新复杂度，而误判的代价被确认步
自身的 fail-safe 兜住（点不动 → `action_failed` → 裁定 `NEEDS_HUMAN`，不会假绿）。grok 同向：
「不致假绿，不升 Critical」。两路一致建议保留，故不改；理由记档于此，不做「已知悉」了事。
