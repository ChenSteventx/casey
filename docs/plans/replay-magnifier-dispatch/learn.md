## 一、同一契约改多层时，每一层都要有自己的钉

「放大镜过滤」契约当初改了编译模板（发射，金牌 S1 钉）、改了回放前置闸（白名单放行，金牌
delete-spec-magnifier 钉），却没人钉**分发层**——于是白名单事件运行时被无条件拒点，且这个洞
在两份冻结金牌的夹缝里活了三天、耗掉三次真机回放才现形。教训成型为一句话：**一份契约横跨
N 层，验收就要 N 个钉；哪层没钉，哪层就是下一个事故现场。**本契约补钉的方式是把判定谓词收
单点（两层共享同一函数）+ 结构钉（判据字面只许在定义处出现、消费方必须走 import）——让
「两层再分叉」这类洞从「等真机爆」变成「金牌当场红」。

## 二、「失败步」要先问「它执行了吗」，再问「它为什么失败」

昨天我把清理步的红解成「删干净后复搜必然候选 0」——一个听起来自洽的机制故事，还写进了
HANDOFF 与取证文档。真相是那两步**从未被执行**：752ms 恰等于事件跑道 `waitForResponse(600ms)`
+ 150ms 收尾的纯等待。识别信号其实一直在场：同一形状在删除前那次（目标还在、图标可见、
定位 unique）也「失败」——「必然候选 0」解释不了它。**当一个失败解释只覆盖一半样本时，
这个解释就是错的**；先用耗时特征对齐执行路径（这次 752ms 与跑道常量逐毫秒吻合），再谈机制。

## 三、耗时指纹是廉价而锋利的诊断器

本契约的定性一锤定音靠的是：752ms ≈ 600+150（没执行，纯收尾）对照 756/758ms（真点击）与
4314ms（收尾+引擎缺席采样窗）。回放跑道里的常量（等待预算、轮询间隔、固定收尾）都是已知数，
任何步的耗时都该能被这些常量的组合解释——解释不了的组合才值得开浏览器抽帧。先对表、后抽帧，
省一轮真机。

## 四、错定性要当场落档更正，别只在新文档里写对的

昨天的错定性已进 HANDOFF 与取证文档。本契约除了写对的新 GRILL，还回到旧取证文档追加了
更正节（指明哪两处错、为什么错、正确结论在哪），并保留其余仍有效的实测数据。**旧文档不更正，
下一个读者就会拿着错定性走一遍我走过的弯路**——文档的陈旧红和金牌的陈旧红一样要清。

## 五、已知边界（评审 R1 pi Medium，裁定记档不收紧）

`isMagnifierSearchClick` 对 `value: ''`（空串）与 `value: '   '`（全空白）按「value 缺」处理——
这**逐字继承**自前置闸原冻结实现（`typeof ev.value !== 'string' || !ev.value.trim()`，
Steven 2026-08-08 裁「value 缺」的落地形），谓词收单点时一个字符没改。评审方（pi）确认：
编译器永不产此形，注入也只点到非破坏图标，无实际安全风险；其建议二选一（记档或收紧）。
取记档不收紧，理由：收紧为 `value == null` 会让前置闸对空串 value 的事件从「白名单放行」变
「具名拒」，越出原冻结裁定的实现语义、且需动冻结金牌换签——为一个证不出风险的边界付换签
代价不值。若未来编译器真产出 `value:''` 的 deleteByName 事件，那是编译器缺陷，按其自己的
契约修，不在本谓词上兜。
