## 1. 教训

- **round-2 双路复核不是「跑一次拿 PASS 就完」**：本契约实现审跑了九轮（`review/*-impl-r1.md` 至 `r9.md`），前五轮各有真发现（`node:vm` 边界、治理缺口等）逐条处置；第六至八轮的三条发现全部落在同一份评审记录文件（`codex-impl-r6.md`）的自述文本与实际处置不一致——即"代码已经改对，但审计记录写错了改了什么"。这提醒：评审记录本身也是可评审对象，异构复核要连带核对"记录是否如实"，不能只核代码。
- **同一处矛盾会连环触发多轮**：`codex-impl-r6.md` 第一次改写只补了主体描述（root.mjs 语义 4 交叉引用），第二轮复核发现改写仍漏了连带更新链路（期望存档副本/`kit-lock.json`/两条 `testChecksums`/两侧提交号）。教训：处置审计记录类发现时要一次性核对"这条改动的全部下游连带证据是否都写全"，别只补最先被指出的那一处，否则会被逐条追加发现、多跑几轮。
- **pi 复核偶发退化**（吐工具调用标签无实质内容）在本轮第七次跑再现；按既有先例（`heterogeneous-review-tooling.md`）追加强调语句重跑即恢复，未升级为异常处置，说明该应对模式稳定可复用。
- **"本次任务在会话介入前已完成大半"是真实存在的场景**：本会话接手时 round-2 已经跑到第五次（`7349441`），记录明写"待再跑一轮确认"。核实历史转录/commit 而非默认从零重做，避免了重复劳动，也避免了误判前序工作已收口。

## 3. 债（含 R2-L1 性能实测数据落账）

### R2-L1：每调用包身份锁（kit-lock）校验的性能预算

设计阶段 `codex` 实测指示值（`review/planreview-codex-r2.md`）：本树十脚本约 64 KB，DrvFs 冷态下空 Node 启动约 0.02 秒、逐文件读取并 sha256 约 0.17 秒。

本次收口补测（本机 WSL2 DrvFs，13 文件包全清单，`node -e` 内联计时，非新起进程）：

| 场景 | 耗时 |
|---|---|
| 逐文件读取 + sha256（第一次，含文件系统冷读） | 136.25 ms |
| 同进程重复校验（热） | 144.55 ms / 129.83 ms |
| 端到端整脚本调用（`node loop-kit/bin/term-lint.mjs --registry`，含 Node 启动 + `shim`/`boot` + 脚本自身逻辑） | 约 480–510 ms |

数据显示两点：① 纯校验本身（约 130–145 ms）在 DrvFs 上比设计阶段单文件级估算（0.17 秒/13 文件折算后量级相当）更平；实测未见明显"热"比"冷"更快的缓存收益，说明 DrvFs 场景下文件系统 I/O 是主导成本、进程内重复读取优化空间有限；② Node 自身启动 + 脚本逻辑占端到端耗时的大头（480 ms 里刨去约 140 ms 校验，仍有约 340 ms 是 Node 启动与脚本本身），即身份锁校验不是当前调用链的性能瓶颈主因。

**预算建议**：以本机实测为准，建议接受每调用 150–200 ms 量级的身份锁校验开销作为可接受预算上限（留有余量应对非 DrvFs 环境更快的场景与 DrvFs 更慢的极端场景）；不建议引入 `mtime` 缓存换速（会削弱完整性，plan.md §7 已明令禁止）；若未来需要提速，方向应是"减少每次编辑触发的 hook 调用次数"（多 hook 叠加是主要放大因素）而非削弱单次校验的完整性。此建议随 route:human #6 呈 Steven 续裁，本文只记账不越权拍板。
