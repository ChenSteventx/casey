# gen-prompts 收口留痕

契约：`gen-prompts`（lane full）。事实源：`docs/plans/gen-prompts/plan.md` + `proposed/GRILL.md`（Steven 2026-07-13 确认「合成走 CLI 外 LLM」形态）+ `loop/prd-gen-prompts.json`（gate 唯一写入 `passes`/`testChecksums`）。本文只记教训、真发现、分歧观察与挂账，不重开设计。

## 1. 教训

- **形态定案要素本身要写死进金牌，别只写进文档**：本契约最大的设计风险是「CLI 外 LLM」这条边界——`casey` 二进制自身绝不接 API key、绝不发网络请求，只出种子模板（`promptset-seed`）与幂等冻结闸（`promptset-freeze`）两段确定性零 LLM 工作。round-1 评审第一条真发现（A1）恰好命中这条边界最薄弱处：金牌哨兵地址与已作废的旧实现（`regress_autotest` 直调 API 形态）默认基址逐字节相同，而自检扫描又漏扫金牌自身——文档上写对了「零网络」，代码上留了一处会让人误以为「这地址是允许出现的」的活化石。教训：凡是「本契约绝不做 X」类硬约束，金牌里连测试夹具本身的字面量都要按同一把尺子扫，不能默认「这是测试数据不算数」。
- **`fresh.length===0` 这类「提前退出」分支是 green-by-construction 自检最容易被绕过的位置**：A4 是本契约最隐蔽的一条——幂等冻结的「0 新增 no-op」路径直觉上「不写盘就不用查」，但坏存量（非法 `source`、撞注入向量库前缀）会在这条路径被悄悄放行成功退出。教训：自检要放在所有提前退出分支之前，「什么都没做」不等于「不需要先确认现状是好的」。
- **符号链接/TOCTOU 类问题在「原子写」实现里默认要假设存在，不能等评审来找**：A3/A8 的固定 `${path}.tmp` sidecar 命名是教科书级符号链接跟随写入风险，本契约实现阶段没有主动想到，靠 round-1 codex 指出。教训：任何「先写临时文件再改名」的原子写模式，临时文件名必须随机化 + `O_EXCL`（`wx` flag），这应作为该模式的默认写法而非事后加固。
- **异构评审跑到第五轮才收敛，属正常量级，不是效率问题**：本契约从 round-1（10 条真发现）到 round-5（双路首次同判 PASS）共五轮，每轮都有真实新发现或未完全兑现的修复被抓出（round-2 抓 A1 处置文档自身残留真实地址、round-3 抓等价编码检测的假阴性回归、round-4 抓协议头场景的过度概括）。教训：「上一轮说修了」不等于「这一轮就该信」，收尾者要认这个节奏是异构复核的正常成本，不要因轮数多而怀疑流程本身出了问题。
- **处置文档/评审材料自身也要过同样的凭据/私网地址扫描**：round-2 codex 指出 round-1 的处置文档（`dispositions-r1.md`）与评审材料（`material-r2.md`）在描述「删除了什么」时把真实地址原样写进了散文和 diff 里——代码改对了，但记录改动过程的文档又把敏感值带了回来。教训：安全类修复收口后，连「记录这次修了什么」的文档本身也要过一遍同样的扫描，不能假设"只是写文档不涉及代码就不用扫"。

## 2. 代码评审逮到的真发现（按严重度，详见 `review/dispositions-r1.md` 至 `r5.md`）

- **HIGH 级 4 条**（round-1）：A1 金牌哨兵地址与作废旧实现真实内网地址一致且自检漏扫金牌自身；A2 CLI 报错把未登记键名/非法 `source` 原值透传进 `stderr`，违 D3 output-seal；A3/A8 同根：`atomicWriteFileSync` 固定 `.tmp` sidecar 名，`writeFileSync` 会跟随预置符号链接写入受害文件；A4 `fresh.length===0` 提前退出跳过 green-by-construction 自检，坏存量在幂等 no-op 重跑时被静默判成功。四条均已红先行验证并修死。
- **MED 级多轮迭代**：A6 地址扫描漏检等价编码写法（IPv6 展开/IPv4 八进制十六进制整数/百分号编码），round-1 修到 round-4 历经「新增覆盖不全→新引入自然语言版本号假阳性→四段收紧引入 CIDR 简写假阴性→显式协议头场景被过度概括进裸文本的『不可靠区分』理由」四轮拉锯，最终收敛为「裸文本恰好四段完整地址 + 显式协议头后的 URI authority 归一化」双通道、显式记录裸文本两三段简写的检测边界为设计取舍并冻结进金牌防静默改动。A7 `N1` 静态扫描可被 helper 转发或字符串拼接绕过，三层防线（import 闭包 + 去注释子串扫描 + 正向允许清单核对调用目标）逐层加固，每层局限均已文档化，非声称完备的对抗性 AST 分析器。
- **LOW 级 2 条**：A9 `--dry-run` 整条候选正文回显收窄为逐条摘要行；A10（pi 独有）补金牌钉「存量藏凭据/私网地址应致 freeze 拒绝」（机制早已存在，只是缺测试覆盖）。
- **round-5 修复者自查主动发现**（非外部评审指出）：`URI_AUTHORITY_RE` 遇 `user:pass@host` 形态 userinfo 时会在内部冒号处提前截断、误把用户名当主机名——同一次收口内主动补 `(?:[^\s/?#@]*@)?` 跳过 userinfo 前缀并红先行验证。

## 3. pi vs codex 差异观察

- **round-1（arb-r1 汇裁）出现一条明确反向 claim 且被证伪**：同一代码区（`fresh.length===0` 分支），codex 判「跳过自检、坏存量被放行」（HIGH），pi 判「0 新增时 `existing.map(canonicalizeEntry)` 会丢弃额外字段、改变字节」（弱反例）。实测复现：该分支根本不落盘（直接 `未写盘 + exit 0`），故 pi 的「改字节」claim 被证伪；codex 的「跳过自检」为机械事实，被采信。这是本契约唯一一次两路给出方向相反结论、且能靠直接实测裁定谁对的场景。
- **覆盖面差异是常态、不构成对弱方的反驳**：round-1 codex 独有 7 条（HIGH2/HIGH3/HIGH4/MED5/MED6/MED7/LOW9），pi 独有 1 条（LOW3，金牌覆盖缺口）；round-2 同样是 codex 给 4 条带文件行号的具体缺陷，pi 判「通过」且未独立发现同类问题——处置文档明确记录「这不构成对 pi 结论本身的反驳，是两路独立评审的正常覆盖差异」。教训沉淀：两路结论不一致时，先看是否有能直接实测复现的机械事实（如上条），没有的话覆盖面深浅不等价于对错，弱方的 PASS 不因强方给出更多发现而被追加倒扣。
- **round-5 双路首次同判 PASS**，且各自独立指出同一个非阻断观察项（`http://[::1]/` 场景下 `URI_AUTHORITY_RE` 捕获组在方括号处截断），两路判断一致确认该现象真实但无实际影响（IPv6 私网地址由既有专属正则独立扫描原始文本兜底，不经过这条新增通道）——是双路首次在同一份材料上给出完全一致结论（含分支性观察项）的一轮，标志异构冗余评审收敛。

## 4. 挂账

- **A5（MED，round-1，codex+pi 独立收敛）term-lint `parseRegistry` 裸 `split('|')` 不认 markdown 转义 `\|`**：根因在复用件 `loop-kit`（独立 sha256 完整性锁定的姊妹包），非本契约新代码缺陷。本契约内已用局部规避（`CONTEXT.md` 第 109 行 `promptset` 词条改用全角 `｜` 分隔枚举值绕开解析歧义），`term-lint --registry` 复跑通过。**挂账 route:human**：`loop-kit` 上游是否要修 `parseRegistry` 以正确处理转义竖线，待另一契约或 Steven 续裁，本契约不越权改复用件。
- **A7 三层防线的各自残余局限**：`N1a`（import 闭包）/`N1b`（去注释子串扫描，可被字符串拼接绕过）/`N1c`+`N1e`（spawn 调用计数 + 正向允许清单）已是本契约范围内可达的最佳努力静态检测，非声称完备的对抗性 AST 分析器。若未来出现更精巧的动态拼接绕过手法，需另开工作项引入真正的 AST 级调用图分析，本契约不在其范围内继续加固。
- **裸文本两三段地址简写（`127.1`/`10.1`/`172.16.5` 等 WHATWG CIDR 简写）显式不检测**：与自然语言版本号/小数无可靠词法区分特征，已作为设计取舍冻结进金牌（`F4c1b`）并注释详述推理，靠凭据兜底门/四段完整形态/IPv6 形态/`route:human` 语义抽检等其他防线兜底。非本契约遗留缺口，是有意识的边界，记录于此供后续契约参考，不需要重新裁定。
- **Dissimilar Redundancy（异构冗余评审）的实际执行族组合如实记账**：本契约的双路复核实际执行是 codex（gpt-5.6-sol）+ pi（deepseek 模型家族），round-5 audit 记录明确标注「实现方=Claude、评审方=deepseek 模型家族，评审族≠实现族」——满足评审家族≠实现家族的铁律，但沿用既有先例记账方式如实标注执行细节，无需额外挂账。
